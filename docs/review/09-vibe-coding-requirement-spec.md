## 1. 这篇文章讲什么

文章回答的是一个越来越常见的面试问题：在 Vibe Coding 和强基座模型普及后，工程师的优势还剩什么？

它的核心不是继续说“AI 写不了复杂业务”。这个说法已经站不稳了。只要上下文足够，AI 可以写微服务调用、状态机、异常处理、并发控制和跨文件修改。真正的差别不在“AI 能不能写代码”，而在谁能让 AI 写出正确、可维护、能上线的代码。

文章把工程师优势拆成五块：

| 优势 | 含义 | 面试里的落点 |
|---|---|---|
| 问题定义能力 | 把一句模糊需求拆成边界、规则、异常和验收标准 | 没有规格，AI 只能猜 |
| 上下文构建能力 | 给 AI 必要代码、业务规则、接口约束，排除噪音 | 输出质量取决于输入质量 |
| 结果验证能力 | 验证业务语义，而不只是代码能不能跑 | AI 最容易写出“合理但错误”的代码 |
| 技术决策能力 | 在业务阶段、团队能力、历史事故和成本之间取舍 | AI 给建议，人做拍板 |
| 成本控制能力 | 控制模型、上下文、Prompt 往返和缓存复用 | AI 编程不是免费资源 |

一句话总结：

> 工程师的优势不是比 AI 手写得快，而是定义问题、组织上下文、验证结果、做工程决策，并控制成本。

解析：

这句话的重点是把竞争点从“人和 AI 谁更会写代码”换成“谁对最终系统负责”。面试官问这个问题时，通常不是想听你贬低 AI，而是想确认你是否理解 AI 编程的真实风险：需求没定义清楚、上下文不完整、代码语义没人验、上线责任没人接。你要回答的是自己在 AI 工作流里的控制点，而不是证明 AI 不行。

## 2. Vibe Coding 和 AI 辅助编程的区别

Vibe Coding 的风险点不是“用了 AI”，而是“不理解、不审查、直接接受”。工程师用 AI 写代码没有问题，问题是把责任也外包给 AI。

| 维度 | Vibe Coding | AI 辅助编程 |
|---|---|---|
| 需求输入 | 一句话描述 | 业务规则 + 约束 + 上下文 |
| 代码理解 | 主要看能不能跑 | 理解行为、边界和影响面 |
| 代码审查 | 大量 accept | 按人工代码同等审查 |
| 线上责任 | 容易甩给工具 | 谁合入谁负责 |
| 验证方式 | 跑通 happy path | 覆盖语义、边界、回归和异常 |

面试里不要说“我不用 AI”。更好的说法是：

> 我用 AI 提升编码速度，但不会把业务理解、技术决策和上线责任交给 AI。AI 生成的代码必须经过同等 code review、测试、trace 和回归验证。

解析：

这个答案要主动承认 AI 是生产力工具，否则会显得脱离现实。但承认之后要立刻补边界：AI 只是生成候选实现，代码所有权仍然在人。面试官真正担心的是候选人会不会“看着能跑就合入”，所以回答里必须出现 review、测试、trace、回归验证和责任归属。

## 3. 重点：一句“加个退款功能”不是需求

产品经理说“加个退款功能”，这只是一句话，不是可执行需求。工程师真正要做的是把它拆成规格。

如果直接把这句话丢给 AI，它大概率会生成一个看起来完整的 `/refund` 接口：传 `order_id`、`amount`，调用支付通道，然后更新订单状态。但真实业务里最容易出问题的不是接口形状，而是这些规则：

1. 哪些订单状态允许退款？
2. 支持全额退款还是部分退款？
3. 运费、税费、手续费怎么处理？
4. 用优惠券支付过的订单，退款怎么退？
5. 多次点击、重试、支付回调重复到达，怎么保证不多退？
6. 第三方支付超时后，本地退款单怎么关闭或对账？
7. 退款成功后，库存、积分、发票、会员权益是否要回滚？

这就是文章最有价值的点：AI 可以写实现，但需求规格必须先被人定义清楚。

解析：

退款功能是典型的“表面是接口，实质是资金状态机”。如果只写一个接口，AI 能很快给出代码；但如果没有金额分摊、优惠券、幂等、超时、回调和对账规则，这段代码越完整越危险。面试里讲这个例子，是为了证明你能把业务语言翻译成工程约束。

## 4. 退款功能：可执行规格答案

下面每个问题都给“答案 + 解析”。答案负责可执行，解析负责说明为什么这样设计。

### 4.1 部分退款怎么处理

建议规则：

1. 退款金额以订单实付金额为上限，不能按商品原价退款。
2. 部分退款必须绑定退款明细：`order_item_id`、数量、实退金额、原因。
3. 商品级退款按优惠后的分摊实付金额计算。例如订单 100 元，用 20 元券后实付 80 元，两个商品各 50 元，则每个商品最多可退 40 元。
4. 运费默认只在全额退款时退；部分退款是否退运费要配置化，例如质量问题可退运费，用户无理由退货不退运费。
5. 手续费、税费、积分抵扣、储值卡支付要作为独立资金分录处理，不能混在现金退款里。
6. 订单状态不能简单改成 `refunded`。需要区分 `partial_refunded`、`refunding`、`refund_failed`、`refunded`。
7. 每次退款成功后更新订单的 `refunded_amount`，下一次可退金额为 `paid_amount - refunded_amount - refunding_amount`。

推荐状态机：

```text
paid
  -> refunding
  -> partial_refunded
  -> refunding
  -> refunded

refunding
  -> refund_failed
  -> refund_closed
```

核心不变量：

```text
sum(success_refund.amount) <= order.paid_amount
sum(success_refund.item_qty) <= order.paid_item_qty
pending_refund + success_refund <= refundable_amount
```

解析：

部分退款最容易错在“按原价退”或“只看本次金额”。正确做法要围绕实付金额、退款明细和累计可退额度建模。订单级字段只能表示汇总状态，真正的可退额度要从资金流水和商品明细推导出来。状态上也不能把部分退款当全额退款，否则后续客服、对账、售后和发票都会读到错误语义。

面试展开：

> 我会把部分退款设计成退款单 + 退款明细，而不是直接在订单上扣金额。每个明细记录商品、数量、实退金额和原因，订单只维护累计退款金额和状态。这样既能支持多次退款，也方便对账和追溯。

### 4.2 退款和优惠券的互斥规则是什么

建议规则：

1. 现金退款只退用户真实支付金额，不把优惠券折算成现金退给用户。
2. 优惠券金额按商品实付比例分摊到订单明细，部分退款时只退该明细对应的实付现金。
3. 全额退款时，优惠券是否返还取决于券规则：未过期且未被作废的可返还，已过期或活动券可不返还。
4. 部分退款默认不返还整张优惠券，避免用户买多件凑满减后退掉部分商品仍保留全部优惠。
5. 如果部分退款导致订单不再满足满减门槛，有两种策略，必须产品先定：
   - 保守策略：退款金额按原分摊结果计算，不追缴已享优惠。
   - 严格策略：重新计算订单优惠资格，退款时扣回不再满足门槛的优惠差额。
6. 券返还要有独立流水：`coupon_restore_record`，不能只改券状态，否则后续对账困难。

推荐面试回答：

> 退款不能直接按商品原价退，要按实付金额和优惠分摊后的金额退。优惠券不是现金，默认不现金化；全额退款是否返券、部分退款是否重算门槛，必须先写成产品规则，否则 AI 写出来的退款逻辑一定会有财务风险。

解析：

优惠券的本质是商家让利，不是用户现金资产。退款如果把优惠券当现金退，会造成资损；如果完全不考虑优惠分摊，又会让用户通过“凑单后部分退款”套利。这里没有唯一标准答案，关键是把策略写清楚：优惠如何分摊、是否返券、部分退款是否重算门槛、返券流水怎么记。

容易踩坑：

1. 满减券订单部分退款后，仍按原优惠退现金，导致用户拿到超过实付的收益。
2. 只改优惠券状态，不记录返券流水，后续客服和财务无法解释。
3. 不区分平台券、商家券、活动券，导致财务归属错误。

### 4.3 多次退款的幂等性怎么保证

建议从三层做幂等：

| 层 | 做法 | 目的 |
|---|---|---|
| API 层 | 客户端传 `idempotency_key`，同一用户、订单、key 只能创建一笔退款请求 | 防止重复点击 |
| 业务层 | `refund_order` 表对 `order_id + refund_request_no` 建唯一索引 | 防止服务重试重复建单 |
| 支付层 | 调第三方支付使用唯一 `out_refund_no` | 防止支付通道重复退款 |

状态流转也要幂等：

1. `refund_success` 回调重复到达，只能第一次更新资金流水。
2. 状态只能单向流转，例如 `success` 不能被后到达的 `processing` 覆盖。
3. 创建退款前要锁订单或使用乐观锁，防止并发退款突破可退金额。
4. 资金变动必须有 ledger（账本）分录，禁止只改订单金额字段。
5. 每次退款请求都返回同一笔退款单的当前状态，而不是再次执行退款。

推荐伪代码：

```python
def create_refund(order_id, amount, idempotency_key):
    existing = refund_repo.find_by_key(order_id, idempotency_key)
    if existing:
        return existing

    with transaction():
        order = order_repo.lock(order_id)
        refundable = order.paid_amount - order.refunded_amount - order.refunding_amount
        if amount <= 0 or amount > refundable:
            raise RefundAmountInvalid()

        refund = refund_repo.create(
            order_id=order_id,
            amount=amount,
            idempotency_key=idempotency_key,
            out_refund_no=next_refund_no(),
            status="created",
        )
        order_repo.mark_refunding(order_id, amount)

    payment_gateway.refund(refund.out_refund_no, amount)
    return refund
```

解析：

退款幂等不能只靠前端按钮置灰。真实系统里重复来源很多：用户重复点击、网关超时重试、服务调用重试、消息重复投递、支付回调重复到达。幂等要覆盖“建单幂等、支付请求幂等、回调处理幂等、状态流转幂等”四个层面。

为什么要锁订单或乐观锁：

并发退款时，两笔请求可能同时看到可退金额充足。如果不加锁，单笔看起来合法，合起来就超额。锁的目标不是把所有退款串行化，而是在计算和冻结 `refunding_amount` 时保护资金不变量。

面试展开：

> 我会用 `idempotency_key` 防重复请求，用唯一 `out_refund_no` 防支付侧重复退款，用状态机防重复回调覆盖成功状态。创建退款时必须在事务里锁订单或用版本号，先冻结退款中金额，再提交支付通道。

### 4.4 退款超时了怎么自动关闭

要先区分两类超时：

| 场景 | 处理 |
|---|---|
| 本地已创建，但还没提交支付通道 | 超过配置时间可关闭，例如 30 分钟 |
| 已提交支付通道，通道处理中 | 不要直接关闭，进入对账或查询状态 |

建议规则：

1. `created` 状态超过 30 分钟未提交支付通道，自动转 `closed`，释放 `refunding_amount`。
2. `processing` 状态超过支付通道 SLA，例如 24 小时，转 `unknown` 或 `reconcile_required`，由定时任务查询支付通道。
3. 对账确认失败后转 `failed`，释放冻结可退金额。
4. 对账确认成功后转 `success`，写入资金流水、更新订单退款累计金额。
5. 自动关闭任务必须幂等，按 `refund_id + expected_status + version` 更新，避免和回调并发冲突。
6. 超时关闭要记录 `closed_reason=timeout`，并发出业务事件，供客服和前端展示。

推荐定时任务：

```text
每 5 分钟扫描：
- created 且 now - created_at > 30m -> closed
- processing 且 now - submitted_at > 24h -> reconcile_required
- reconcile_required -> query payment gateway -> success / failed / keep_waiting
```

解析：

超时不能简单等同于失败。只要请求已经发给支付通道，本地就不能擅自关闭，因为通道可能稍后成功退款。如果本地关闭但通道成功，就会出现订单状态和资金事实不一致。正确做法是区分“未提交可关闭”和“已提交需对账”。

自动关闭任务的关键是并发安全：定时任务、用户重试和支付回调可能同时操作同一退款单。更新状态时要带 expected status 或 version，例如只允许 `created -> closed`，不能把已经 `success` 的退款单关掉。

面试展开：

> 我会把超时分成未提交超时和通道处理中超时。未提交可以关闭并释放冻结金额；已提交只能进入对账状态，由定时任务查询支付通道，确认成功或失败后再更新本地状态。

### 4.5 可直接交给 AI 的 Prompt

如果要让 AI 写退款功能，不要说“写一个退款接口”。可以这样给：

```text
请实现订单退款功能。约束如下：

1. 支持全额退款和部分退款。
2. 退款金额不能超过订单实付金额减去已成功退款和退款中的金额。
3. 部分退款按 order_item 维度申请，按优惠分摊后的实付金额计算可退金额。
4. 优惠券不折现退款；全额退款时可按券规则恢复，部分退款默认不返还整券。
5. API 必须支持 idempotency_key，同一 order_id + idempotency_key 重复请求返回同一退款单。
6. 第三方支付 out_refund_no 必须全局唯一。
7. refund_success/refund_failed 回调必须幂等，状态只能单向流转。
8. created 超过 30 分钟未提交支付自动关闭；processing 超过 24 小时进入对账状态。
9. 所有资金变化必须写 ledger，不允许只更新订单金额字段。
10. 请补充单元测试：全额退款、部分退款、优惠券分摊、重复请求、重复回调、超额退款、超时关闭。
```

这个 Prompt 的价值不在措辞，而在它把业务规则、状态机、幂等、资金账本和测试要求都给全了。

解析：

这个 Prompt 的本质是“规格化输入”，不是普通提示词优化。AI 写业务代码时最怕缺上下文，所以要把不可违反的不变量、状态流转、幂等键、第三方接口约束和测试场景一次给全。否则 AI 会按通用电商理解补空白，而那些空白正是线上事故来源。

怎么判断 Prompt 是否合格：

1. 读完后能不能写出数据库唯一约束。
2. 能不能写出状态机。
3. 能不能写出异常和超时路径。
4. 能不能写出测试用例。
5. 能不能解释为什么不能超额退款。

## 5. 上下文构建：别让 AI 猜系统

写复杂业务时，要给 AI 的上下文至少包括：

1. 业务规则：什么能做、什么不能做。
2. 数据模型：订单表、支付表、退款表、资金流水表、优惠券表。
3. 状态机：订单状态、退款状态、支付状态如何流转。
4. 上下游接口：支付网关、库存、积分、发票、通知。
5. 异常策略：超时、重试、失败、回滚、对账。
6. 代码约束：框架、事务、锁、日志、错误码、测试风格。

不要把整个代码库都塞给 AI。更好的方式是：先给接口和相关领域模型，再按需补充具体实现文件。上下文越精准，AI 越不容易被无关代码带偏，也越省 token。

解析：

上下文构建不是“给得越多越好”，而是“刚好覆盖决策所需信息”。如果让 AI 自己在全仓库里找，它会消耗大量 token，还可能被旧代码、测试 fixture、无关模块误导。高手用 AI 时，会先明确当前任务的领域边界，再给相关模型、接口、状态机和局部实现。

面试展开：

> 我一般会把上下文拆成三层：必须知道的业务规则、必须遵守的接口和数据模型、需要修改的局部代码。先给前两层让 AI 形成正确约束，再按需给具体文件。这样比直接喂整个仓库更稳定，也更省 token。

## 6. 结果验证：重点看语义，不只看运行

AI 生成代码最危险的地方，是它经常“看起来合理”。退款这种业务尤其要验语义：

| 验证项 | 示例 |
|---|---|
| 金额正确 | 部分退款金额是否按实付分摊，而不是按原价 |
| 对象正确 | 退到原支付账户，不能退到当前登录用户的任意账户 |
| 状态正确 | 部分退款后订单不能误标为全额退款 |
| 幂等正确 | 重复请求、重复回调、服务重试都不多退 |
| 并发正确 | 两笔退款同时发起不会突破可退金额 |
| 对账正确 | 支付通道超时后能查询并修正本地状态 |
| 回归正确 | 库存、积分、优惠券、发票、售后单不被破坏 |

面试里可以说：

> 我审查 AI 代码时，不只看语法和测试是否通过，而是先看业务不变量有没有被维护。比如退款功能，我会重点验证实付金额、优惠分摊、订单状态、幂等键、支付回调和资金流水。

解析：

AI 代码的风险不是“完全不能跑”，而是“跑得通但语义错”。退款成功返回 200 不代表钱退对了；单测通过不代表并发退款不会超额；回调处理没报错不代表重复回调不会写两笔账。验证时要先列业务不变量，再看代码是否维护这些不变量。

可复述的验证顺序：

1. 看金额不变量：不能超过实付，不能超过可退。
2. 看状态不变量：成功不能回退，关闭不能覆盖成功。
3. 看幂等不变量：重复请求和重复回调只产生一笔资金影响。
4. 看回归影响：库存、积分、券、发票、售后状态是否同步。

## 7. Token 成本怎么控制

文章里这部分可以总结成五条：

1. **模型路由**：简单补全、文档、局部修改用小模型；架构设计、复杂重构、代码审查用强模型。
2. **上下文管理**：只给相关代码和接口，不把整个仓库一次性塞进去。
3. **Prompt 一次说清楚**：目标、约束、数据结构、边界和测试一起给，减少来回返工。
4. **缓存和模板复用**：CRUD、校验、错误处理、测试样例可以模板化，让 AI 填差异。
5. **任务评估**：一行配置、明确空指针、简单重命名，手工更快就不要调用 AI。

面试回答：

> 我不会把 AI 当成无限免费的工程师。简单任务走低成本模型，复杂任务才用强模型；上下文只给相关文件；常见代码用模板复用；能 10 秒手改的就不发给 AI。成本控制不是省到不能用，而是在质量和 token 之间做工程取舍。

解析：

这个问题考的不是你能不能背“模型路由”，而是你是否知道 AI 编程有工程成本。token 成本来自模型等级、上下文长度、往返次数和重复生成。真正的优化不是一味省钱，而是把强模型用在高价值任务上，把低价值任务模板化、缓存化或手工处理。

面试展开：

> 我会按任务复杂度和风险分层。简单修改、文档和样板代码用低成本模型或模板；复杂重构、架构设计和代码审查用强模型。上下文只给相关文件，Prompt 尽量一次说清楚，减少来回返工。成本控制和质量控制要一起做。

## 8. 面试高频问答

### Q1：AI 越来越强，你的优势是什么？

差的回答：

> AI 写不了复杂业务。

更好的回答：

> AI 确实能写很多复杂代码。我的优势不是否认 AI，而是让 AI 产出可上线的代码：我负责定义问题、补齐上下文、验证业务语义、做技术决策和控制成本。没有这些，AI 生成的代码只是“看起来可用”。

解析：

这个回答先承认 AI 强，避免陷入“AI 不行”的防守姿态；然后把人的价值放在 AI 之前和之后：之前负责定义问题和构建上下文，之后负责验证结果和承担上线责任。这样回答比“AI 写不了复杂业务”更稳，因为模型越强，这套逻辑越成立。

可加一句项目化表达：

> 在 Agent Runtime 项目里也是这个思路：LLM 做 planner，但 DAG 装配、schema 校验、状态恢复和执行 guardrail 都由工程系统负责。

### Q2：你负责的项目里，哪些让 AI 写，哪些自己写？

回答：

> 我看两个因素：出 bug 的代价，以及 AI 生成加审查的总成本。样板代码、测试骨架、重复性实现适合 AI；涉及资金、安全、权限、合规、核心状态机的代码，即使用 AI 生成，也必须人工逐行审查和补充测试。非常明确的小改动，手写更快就手写。

解析：

这题不要按“AI 能不能做”来分，而要按风险和总成本来分。AI 能写，不代表值得让它写；你能手写，也不代表不用 AI。资金、安全、权限、核心状态机属于高风险区域，AI 可以辅助，但不能无审查合入。样板代码、测试骨架、重复 CRUD 属于低风险高重复，适合让 AI 提速。

可复述判断公式：

```text
是否交给 AI = 任务重复度高不高 + 业务风险大不大 + 我审查它的成本是否低于手写
```

### Q3：AI 代码出了线上问题怎么办？

回答：

> 处理方式和普通线上 bug 一样，先止血，再定位，再补流程。先回滚或降级恢复服务；再通过日志、trace、监控定位具体行为；最后补测试、补 review checklist，并复盘为什么 AI 生成或人工审查没拦住。关键不是甩锅给 AI，而是把 AI 代码纳入同一套工程责任。

解析：

面试官问这题，是在看你会不会把责任推给工具。正确态度是：AI 写的代码也是团队代码，线上事故按同一套 SRE 和研发流程处理。区别只在复盘时要额外分析 AI 使用流程：需求是否没写清、上下文是否缺失、审查 checklist 是否没有覆盖、测试是否没有覆盖语义边界。

回答层次：

1. 先止血：回滚、降级、开关关闭、补偿。
2. 再定位：日志、trace、指标、资金流水或业务事件。
3. 后修复：补代码、补数据、补测试。
4. 最后补流程：更新 AI 使用规范和 review checklist。

### Q4：怎么管理 AI 生成代码？

回答：

> 谁 accept 谁负责。AI 代码走同样的 code review、测试、静态检查和发布流程。团队还要定义哪些项目能用 AI、哪些敏感代码不能上传，配置 `.gitignore`、`.claudeignore` 或企业版隔离策略，避免工具读取密钥、核心算法、交易策略和客户数据。

解析：

AI 代码管理要覆盖两类风险：质量风险和合规风险。质量上，AI 生成代码不能绕过 review、测试、扫描和发布门禁；合规上，要控制哪些代码能被模型服务读取。尤其是密钥、客户数据、交易策略、核心算法和未公开业务逻辑，不能因为工具方便就直接上传。

面试展开：

> 我会把 AI 代码当成普通代码管理，但额外加两条边界：一是敏感文件通过 ignore 和权限隔离不进入 AI 上下文；二是对 AI 生成代码统计缺陷类型，反过来优化 Prompt、上下文模板和 review checklist。

## 9. 最终记忆点

这篇文章可以和你的 Agent Runtime 经验连起来讲：

1. **AI 编程也是 Agent 工程**：输入、上下文、工具、验证、成本都要治理。
2. **需求规格是第一道 guardrail**：一句话需求不能直接变代码。
3. **工程师价值从“手写代码”转向“定义和验证系统行为”**。
4. **越强的 AI，越需要强工程边界**：状态机、幂等、审查、测试、trace、回滚和成本预算。

一句可背版本：

> Vibe Coding 的问题不是用了 AI，而是没有规格、没有上下文、没有验证就接受代码。我的价值是把模糊需求变成可执行规格，把代码生成放进工程闭环，让 AI 写得更快，也写得更对。
